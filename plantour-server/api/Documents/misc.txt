Как должен работать механизм управления юзерами с учетом Админ / Участник

Админ

- Решает организовать путешествие. 
- Создаёт запись в табице trips.
- Решает пригласить людей в путешествие. 
- Создаёт записи в таблице travelers с полем user_id = null, которая указываент на приглашённого человека, если такие записи ещё не существуют.
- Добавляет записи в invitations. Сервис рассылки приглашений рассылает приглашения.

Участник

- Получает приглашение, как правило, email

- В email содержатся две ссылки, по которым участник может перейти, чтобы зарегистрироваться как участник путешествия:
	1) web ссылка с одноразовым токеном; 
	2) 8 символьный код доступа к Plantour в рамках одного путешествия.

- Когда участник регистрируется действие одноразового токена прекращается, invitations.accepted_at получает значение, в таблицу trip_travelers добавляется запись и копируется access_code из invitations. Постоянный токен запоминается на локальном компе участника.

- Когда участник следующий раз захочет получить доступ к Plantour c того же компа он перейдет по plantour адресу, приложение прочитает токен из local storage и учасчтнику логиниться не придётся. Если по какой-то причине токен не сработает, участнику придётся ввести свой код доступа, полученный в приглашении.
